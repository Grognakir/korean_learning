# Обязательные условия перед каждой итерацией

Последнее обновление: 2026-08-08

## 0. Когда читать

Исполнитель **обязан полностью прочитать этот документ** перед началом любой итерации фазы 1 (`F1-I*`, `fix/*` по CP, checkpoint-ветки) и перед любым коммитом, затрагивающим training UI, AppShell, navigation или session layout.

Этот файл — рабочий preflight. Он не заменяет карточки итераций. При расхождении приоритет:

1. Корневой и вложенные `AGENTS.md`
2. Этот документ
3. `docs/PHASE_1_REMAINING_IMPLEMENTATION_PLAN.md`
4. `docs/APPLICATION_PLAN.md`
5. Фактические публичные контракты кода
6. Детали воспроизведения UI-дефектов — `docs/PHASE_1_UI_AUDIT_FINDINGS.md`

## 1. Чеклист перед кодом

Отметить фактически, не формально:

1. Рабочее дерево не содержит пересекающихся чужих изменений; несвязанное не трогать.
2. Предыдущая итерация `done`, её коммит есть в истории; checkpoint (если нужен) подтверждён пользователем.
3. Создана **только** ветка текущей карточки от коммита предыдущей; следующую итерацию не начинать.
4. Прочитана карточка текущей итерации целиком: результат, файлы, тесты, «не делать», DoD.
5. Для затрагиваемых API прочитаны локальные Next.js guides в `node_modules/next/dist/docs/`.
6. Baseline gate зелёный на Node.js `24.18.0` / pnpm `10.34.5`:
   `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test:run`, `pnpm build`
   (+ `test:integration` / `test:e2e` / `test:db` / `test:rls`, если уже существуют в проекте).
7. Если baseline красный — feature не начинать; локализовать причину и сообщить.

## 2. Протокол одной итерации

- Ровно одна итерация за шаг: scope только текущей карточки.
- Тесты добавляются вместе с кодом; существующие тесты не ослаблять ради зелёного прогона.
- После кода: полный gate раздела 1.6 → secret scan → обновить `docs/APPLICATION_PLAN.md` и полностью перезаписать `.Codex/sessions/current.md` → один содержательный коммит с сообщением из карточки.
- Отчёт по формату раздела 28 исполнимого плана; **остановиться**; не создавать ветку и код следующей итерации в том же шаге.
- Дефект предыдущего слоя → отдельная `fix/*`, не маскировать внутри следующей feature.
- Push / PR / merge / Vercel / Supabase / credentials — только по правилам раздела 4.6 плана и только после явного разрешения пользователя на соответствующий CP.

## 3. Архитектурные запреты (постоянные)

- Направление зависимостей: `app → features/modules/components/wrappers → lib/types`; обратные запрещены.
- Общий training engine не импортирует `src/modules/honorifics`.
- React-компоненты не содержат правил оценки, подсчёта прогресса или грамматики.
- Server Components по умолчанию; Client Components только для состояния, событий, hooks и browser API.
- DB rows не в UI напрямую: mapper + Zod.
- Correct answers / `is_correct` не в публичном DTO до submit.
- Service-role key не в браузерном графе.
- Timestamps в domain/session/storage — ISO-строки; состояние JSON-сериализуемо.
- Случайность в тестируемом domain — только seed или инъекция.
- Документы проекта только в `docs/` (исключение: `.Codex/sessions/current.md`).
- Не создавать README/ADR/changelog вне scope карточки.

## 4. Инварианты учебной сессии и layout (после CP-1A)

Нарушение любого пункта = дефект; нельзя «чинить» повышением `z-index` панели действий над мобильной навигацией.

### 4.1. Мобильные действия и навигация (UI-001 / UI-002)

- На ширинах **&lt; 48rem** панель действий учебной сессии **не sticky**: она в обычном потоке после содержимого.
- Sticky actions допустимы только с **`min-width: 48rem`**; `bottom` берётся из наследуемого `--training-actions-sticky-offset` страницы, не из magic number.
- Кнопка `Ответить` / `Дальше` не пересекается с мобильной навигацией (пересечение 0 px).
- Панель действий не перекрывает варианты, поля, feedback и контролы задания.
- Учитывать `env(safe-area-inset-bottom)` и резерв высоты mobile nav в `AppShell`.
- `TrainingShell`: grid `minmax(0, 1fr) auto`; `.content` — явная grid-область с gap; не полагаться на gap внешнего shell для внутренних блоков.
- Кнопка 100% ширины только до **30rem**; на больших ширинах сохранять компактную ширину (~8rem / 128px), если так уже принято.

### 4.2. Скроллбар и центрирование (UI-003)

- На корневом scroll container сохранять `scrollbar-gutter: stable both-edges`.
- Не заменять это принудительным `overflow-y: scroll`.
- Появление/исчезновение вертикального скроллбара не должно сдвигать контент по горизонтали.
- Горизонтальный overflow на 320–2560 px запрещён.

### 4.3. Семантика прогресса (UI-004)

Утверждена модель **прогресса выполнения** (не путать с позицией):

- Текст позиции: `Задание current из total` (`selectProgress.current` не ломать).
- Полоса: `value = answeredCount`, `max = total`.
- До первого ответа: позиция `1 из N`, `aria-valuenow="0"`.
- После ответа до `Дальше`: полоса уже `answeredCount`.
- На последнем задании до ответа: `N - 1`; после принятия последнего ответа: `N`.
- Accessible name: `Выполнено заданий: X из N`.

### 4.4. Клавиатура и отправка ответа (UI-005)

- Отправка ответа из однострочного поля и кнопки `Ответить` работает предсказуемо с клавиатуры (Enter отправляет готовый ответ; пустой/неполный — нет).
- `Дальше` не срабатывает от Enter в уже отвеченном поле.
- Нет глобального `keydown` на `document`.
- В многострочном поле Enter = новая строка, не отправка.
- После `Дальше` фокус на heading/области нового вопроса.
- Реализация — через кастомную форму/композицию проекта (§4.7), а не через необработанное поведение нативного browser form chrome.

### 4.5. Язык контента (UI-006)

- Самостоятельные корейские фрагменты помечены `lang="ko"`.
- В смешанном RU+KO языке — `lang` на вложенном элементе, не на всём русском предложении.
- Не менять доменное поле `level: "1급"` ради разметки.

### 4.6. Типографика prompt (наблюдение после аудита)

- Не полагаться на глобальный `text-wrap: balance` у `h2` для учебных prompt, если он даёт ложные переносы; для `.promptHeading` предпочитать обычный перенос по словам.
- `overflow-wrap: anywhere` использовать только если доказан риск overflow; иначе `break-word`.

### 4.7. Кастомные формы и списки (постоянное требование продукта)

**Запрещено** использовать нативные браузерные контролы форм и выпадающих списков в пользовательском UI:

- не использовать нативный `<form>` как визуальный/поведенческий каркас продукта, если он тянет за собой нативную стилизацию или нативную семантику submit/reset, с которой нельзя согласовать дизайн-систему; интерактивные формы собирать из кастомных композиций проекта (поля, кнопки, валидация, focus management) с предсказуемой клавиатурой и touch-целями;
- **запрещены** нативные `<select>`, `<datalist>` и браузерные dropdown/combobox как способ выбора значения в UI;
- разворачивающиеся списки (dropdown, combobox, matching «правое значение», любые picker'ы) — **только кастомные** компоненты: открытие/закрытие, список опций, индикатор, отступы, focus ring и keyboard (Arrow/Enter/Escape/Tab) контролируются приложением;
- нативный `<input type="radio|checkbox">` допустим только если он визуально полностью перекрыт кастомной оболочкой design-system **или** заменён кастомным контролом с той же a11y-ролью; «голый» системный вид запрещён;
- текстовый ввод (`input`/`textarea`) допускается как основа поля, но оформляется только через общие UI-примитивы проекта (`Input`, `Textarea` и т.п.), без сырого системного вида вне design-system;
- цели нажатия ≥ 44×44 px; у кастомного dropdown стрелка/шеврон не прилипает к краю — явный `padding-inline-end` и место под иконку.

`MatchingExercise` использует общий кастомный `Select` (`src/components/ui/Select`); учебная сессия собирается кастомной композицией без нативного `<form>` / `<select>`.

## 5. Тесты и проверка UI

- Новые поведения покрывать unit/component tests рядом с кодом.
- **Не** писать фиктивные JSDOM-тесты на имена CSS-классов как замену геометрической регрессии sticky/fixed.
- До Playwright (F1-I22) геометрия UI-001–UI-003 подтверждается ручной browser-проверкой по матрице из `docs/PHASE_1_UI_AUDIT_FINDINGS.md` §6.9, если итерация трогает session layout / AppShell / navigation / globals scrollbar.
- После F1-I22 сценарии UI-001–UI-003 переносить в `tests/e2e/training.spec.ts`.

## 7. Runtime

- Local/CI: точные Node.js `24.18.0` (`.nvmrc`) и pnpm `10.34.5`.
- Молчаливый fallback на другую версию запрещён; смена pin — отдельное согласование + полный gate.
- Vercel: Node `24.x` в диапазоне `engines`, pnpm из `packageManager`.

## 8. Короткий запрет «не делать между итерациями»

- Не начинать следующую feature в том же шаге.
- Не пушить промежуточные iteration branches (кроме исключений плана: preview/CP).
- Не публиковать draft honorifics; не тащить preview в production composition.
- Не добавлять OpenAI, password login, OAuth, payments, SM-2/FSRS, Storage bucket, админку.
- Не ставить Playwright раньше F1-I22.
- Не расширять MVP «заодно».
- Не вводить нативные `<select>` / системные dropdown и не оставлять «голые» нативные формы вне design-system (§4.7).
